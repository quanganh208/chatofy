# STT latency and content loss — timeouts, loss visibility, lane semaphore

User reported STT "quá chậm, mất từ mất nội dung rất nặng" with CPU/RAM nearly idle, deployed at ssh.quanganh208.dev. Diagnosis (all measured read-only on prod): single-request STT is fast (vi 70-80ms, en 135-200ms for 6-8s clips) — the sidecar serialized every decode behind one `threading.Lock` per engine while the api fans out ~26 partial re-decodes + up to 4 uncancelled speculations + a final per turn; 6 concurrent requests took the same wall time as 6 serial (FIFO staircase to 6x), machine ~72% idle, CPU peak 447% of one core. The Cloudflare tunnel was exonerated (55-64ms steady-state on a reused connection; the scary 207/978ms first numbers were per-connection TLS handshake). User confirmed load is 1 person / 1 tab, and measured saturation needs ~3 concurrent sockets, so priority was reordered per the brainstorm contract's own risk #2: the unbounded Gemini tail (max 8943ms, no timeout anywhere on any provider call) pushing turns into `too_many_turns` until the client silently discarded buffers was the primary symptom driver, not the lock.

Delivered:

1. `fetchWithDeadline` helper + budgets on all six provider fetches including ElevenLabs (found by code review) — STT/embed/voices 5s, TTS 15s, ElevenLabs 30s — and Gemini `httpOptions.timeout` 20s (field name verified against the SDK reference).
2. Client loss visibility: `send()`/`sendAudio()` return boolean; `sentMs`/`sequence` advance only on a frame that left the socket; failed sends hold and re-flush in order with no sequence hole (the server rejects a sequence that moved with a gap); orphaned-block counter + log; `'dropped_pending'` added to `UnheardReason` so the existing unheard marker renders.
3. Sidecar concurrency: the plan's step-1 experiment decided a **lane Semaphore over the ONE recognizer**, not a pool of copies — 120 concurrent decodes produced byte-identical transcripts on both engines, concurrent decodes scale ~2.3x on the shared ONNX session, and zero extra memory removes the OOM risk entirely. `LOCAL_STT_CONCURRENCY` default 4 (clamped ≥ 1), saturation refuses with 503 after `LOCAL_STT_LANE_WAIT_MS` 2000ms.
4. Duty-stretched partial cadence `max(300ms, 3 × lastDecodeMs)` — implementing the repo's own measured-but-never-implemented conclusion, killing the amplifier where slower decodes bought the scheduler a _higher_ lane share.

A speculation in-flight cap was implemented and **reverted** — the turn-session/translation-session specs proved renewal suppression costs the measured 870ms head start (guess 1 is stale either way; guess 2 is the only reusable one). Also measured on prod: `LOCAL_STT_THREADS=4` is already optimal (swept 1/2/3/4/8; threads=8 is ~25% slower per decode at 1325% CPU vs 447% — ONNX intra-op oversubscription); dev's default 8 is the slower one. `TURN_METRICS_PATH` enabled on prod per user decision (it was disabled 2026-09-01 for logging sessionIds+timestamps; schema verified narrow: per-conversation UUID + timings, no transcript/audio/user id), stale rows archived, pre-fix baseline accruing from real usage.

Tests: api 879, realtime-client 334, web 833, sidecar pytest 27, ai-providers 4 (new vitest harness; its tsconfig moved to the relative `extends` form because the package-export form breaks Vitest's transform). Review gates ran as tester + code-reviewer subagents; review findings addressed (ElevenLabs deadlines, in-order guards for flapping transports, concurrency-test robustness via Moonshine + a discarded warm-up burst). Follow-ups recorded: final-over-partial lane priority (absent; arrival-order luck under saturation) and the TTS sidecar's identical lock.

One environment trap: web's `eslint --fix` mutates `same-origin-path.ts` by deleting a mandatory cast (documented in that file's own comment; only the next build catches it). Restored; build green.
