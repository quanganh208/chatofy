# Code review — `feat/pluggable-languages` vs `main` (merge base c082da4e)

Date: 2026-09-28 (Asia/Saigon). Read-only review. docs/ excluded.

## Scope

- 148 files under apps/packages (+10 under services), ~4.7k/-1.3k LOC. Focus: migrations + store paths, wire/HTTP compat, translate pipeline, realtime-client socket refactor, web display, glossary security, hidden two-language assumptions.
- Evidence: diff reading; scratch zod probe (tsx, scratchpad only) against `glossaryEntrySchema`, `saveConversationRequestSchema`, `transcriptSegmentWireSchema`; body-size estimate script; `vitest run` in packages/types (88 pass) and packages/realtime-client (pass).

## Overall

Migrations and backfill are correct and match the runtime invariant. Wire/HTTP compat for legacy payloads holds (probed). Glossary cap applies to every key and prompt bytes are unchanged for `{vi,en}` input. Two real client regressions came in with the refactors: the live target pane goes blank when you swap direction after a conversation, and a socket closed mid-handshake is no longer closed. The save path also has a size-budget problem and a strictness gap.

Count: critical 0, high 2, medium 2, low 7.

- **Read path**: `primaryTranslation(turn, languages)` rebuilds the legacy `targetText` for both directions. `legacyDirectionOf` rebuilds `direction` from the declared-source-first array.

## High

### H1. Live target pane goes blank after swapping direction once a conversation has ended

- `apps/web/src/components/translate/transcript-panes.tsx:100,117`: `target={to}` comes from the CURRENT `settings.direction`.
- `apps/web/src/components/translate/conversation-transcript.tsx:358`: `groupTranslation(group, target)` → `display-groups.ts:226`: `turn.translations[language] ?? ''`.
- Swap is enabled whenever the session is not running (`panel-headers.tsx:167 disabled={running}`). Nothing resets the transcript on a direction change (checked `cascade-panel.tsx`).
- Scenario: run a vi→en conversation, stop, click swap. Every finished block's translation line now reads `translations.vi`, which those turns never had, so the target pane is empty. On main, `groupTargetText` showed each turn's own `targetText`, whatever the settings said. The same happens after a reload-restored settings change while a transcript is still on screen.
- Fix: derive the pane language per turn, not from settings. For example, keep the conversation's direction as it was captured at start and pass that (`useConversationSave` already needs the same value). Or render `groupTranslation(group, directionLanguages(group.turns[0].direction).target)`. Add a spec: stop, swap, and the translation text stays.

### H2. Socket refactor: `close()` during the handshake no longer closes the socket, and LiveSession then starts an orphan Gemini Live session

- `packages/realtime-client/src/transport/live-translate-socket.ts:73` and `translate-socket.ts:91` now do `this.socket = await connectJsonSocket(...)`. The field is assigned only AFTER the handshake resolves. On main it was assigned synchronously before the await.
- As a result, `close()` (`live-translate-socket.ts:119`, `translate-socket.ts:179`) during CONNECTING sees `this.socket === null` and does nothing. The pending socket later opens and gets installed with live handlers. The same applies to two overlapping `connect()` calls: the first socket is never tracked, so `this.close()` in the second call cannot close it, and one socket leaks.
- Concrete path: `packages/realtime-client/src/conversation/live-session.ts:102-109`. The extension live mode (`apps/extension/src/live-direction-session.ts`) calls `dispose()` (`:160`) while `await socket.connect()` is pending (user presses Stop or switches mode during connect). `dispose` → `LiveTranslateSocket.close()` does nothing. The handshake completes and `socket.start(direction)` runs (there is no stale check), so the server opens a Gemini Live upstream that nobody consumes. Then `server.live.ready` reaches `onEvent` (`:169`), which sets `status='live'` and fires `listeners.onReady` on a disposed session. On main the same race left the promise pending forever and never sent `start`.
- `ConversationSession` is saved by its own `isStale()` check after connect. LiveSession is not.
- Fix: keep the pre-refactor contract. Have `connectJsonSocket` return the socket synchronously (plus a `ready` promise), and let the owner assign `this.socket` before awaiting. Or pass an `onCreated(socket)` callback. Also add a stale/status check in `LiveSession.connect` after the await (`if (this.status === 'stopped') { socket.close(); return; }`). Add a spec: `close()` before `onopen` means `ws.close` is called and `onEvent` never fires.

## Medium

### M1. Save body now carries every translation twice; the "400k chars ↔ 1 MB parser" pairing is silently broken

- `packages/types/src/http/conversations.ts:33,41` documents `MAX_TOTAL_CHARS` and the 1 MB `/conversations` limit (`apps/api/src/common/middleware/narrow-body-limits.ts:245`) as one decision that moves together. The current client now sends `translations` AND the legacy `targetText` (`conversation-turns.ts:147-149`). The refine (`conversations.ts:231`) counts only `translations`.
- Measured with a synthetic body (scratch script), 400k chars en→vi: 400 turns go from 0.50 → 0.78 MiB, 800 turns from 0.56 → 0.85 MiB. A translation-heavy en→vi conversation with repaired `displayText` gets close to 1 MB. Past it, express answers 413, which is not retryable, and the conversation never reaches history.
- Fix, pick one and record it next to `HISTORY_LIMITS`: raise the `/conversations` JSON limit (e.g. 1.5–2 MB) and update the comment, or count `targetText` in the refine so the cap reflects the bytes actually sent.

### M2. Save schema does not tie turn language fields to each other or to `targetText`; `targetText` is silently discarded

- `conversations.ts:106-109`: `sourceLanguages` and `translations` are validated only against the registry. `conversations.service.ts:358` then stores `translations` and drops `targetText` (`toTurnWrite`).
- Probe: `translations: {}` with `targetText: 'xin chao'` is ACCEPTED. The row is stored with no translation and reads back `targetText: ''`. Also accepted: `sourceLanguages:['en']` on a `speaker_a` turn, `sourceLanguages` outside `languages`, and a translation keyed by the source language. History then shows `primaryTranslation` = '' for those rows.
- No current client path emits this. The server-built segment always has `translations[spoken]`. But this is exactly the kind of silent loss that strict server validation is supposed to catch, and the check costs little.
- Fix: add a `superRefine` on the request shape. Require `sourceLanguages ⊆ languages`, every `translations` key ∈ `languages \ sourceLanguages`, and `translations` non-empty whenever `targetText !== ''`. Or, when `translations` is empty, fill it from `targetText` in the preprocess, not only when both fields are absent.

## Low

### L1. `/translate/voices` leaks the cache's `expiresAt` on cache hits

`pipeline-translator.service.ts:440`: `return cached;` returns the cache entry `{voices, speedAdjustable, expiresAt}` by reference, so the controller serialises `expiresAt`. A cold call (`:450`) returns `catalog` without it, so the response shape depends on cache state. Fix: `return { voices: cached.voices, speedAdjustable: cached.speedAdjustable }`.

### L2. Glossary read drops rows that fail the current schema; the editor's next full-replace PUT then deletes them permanently

`prisma-translation-context.store.ts:334,351` log and filter them out. Rows written before `e8b76cb8` (the punctuation-aware 4-word count landed an hour after the table, `50ca99d4`), or rows with a key from a later-added-then-rolled-back registry language (`"Unrecognized key"`), vanish from `/preferences`. Saving the context then removes them from the DB. On main the store returned every row. Fix: before release, run a read-only psql count of rows failing the cap. Or surface dropped-row count in the response and editor instead of just logging.

### L3. Speed control disappears for English while the catalog is loading or failed, or against an older API/TTS sidecar

`voice-settings-panel.tsx:61` uses `catalog.speedAdjustable`, which is `false` in the loading and failed states (`use-voice-catalog.ts:89,124`) and when an older sidecar or API omits the field (`api-client.ts` `.default(false)`, `local-speech-tts-provider.ts` `?? false`). On main the slider always showed for `vi_to_en`. This is a deploy-order regression: an old TTS sidecar behind the new API hides a working control. Fix: accept it and note it in the release steps (deploy sidecars first), or keep the last known value while loading.

### L4. One corrupt `languages` row returns 500 for the whole history list

`prisma-conversation.store.ts:599`: `legacyDirectionOf` throws on fewer than two codes, inside `toSummary`, which `list()` maps over every row. The write side prevents this, so it is only defence-in-depth. If you want isolation, log the row and skip it rather than throwing.

### L5. REST refusal returns 400 for a server capability gap

`translate.controller.ts:114` returns `BadRequestException("This server cannot recognise …")`. The client did nothing wrong. The WS path uses the `language_unavailable` code. 503 (or 422 with a code) fits better, and 400 implies "fix your request".

### L6. `SpeechLanguageSupport` logs a warning every 60 s per unserved registry language

`speech-language-support.ts:119-120`: `warnMissingEngines` runs on every refresh, so a deployment that deliberately runs without one engine gets a warning a minute forever. Fix: warn only when the served set changes.

### L7. Plan references left in code comments (violates the "Stable Code Artifacts" rule)

`apps/api/src/modules/translate/session/turn-language-plan.ts:44` ("a non-goal this plan defers"), `session/language-identifier.ts:17-18` ("the seam this plan builds for"), `services/translation-session.service.spec.ts:2991` ("The durable fan-out proof this plan exists for"). Rewrite them to state the invariant.

## Remaining two-language assumptions (informational)

- `speakerRoleFor` (`languages.ts`) is binary: with three or more languages, every non-first language maps to `speaker_b`. `fillTurnLanguages` then inverts `speaker_b` to the FIRST non-first language, which is ambiguous past two. This is fine while the compat shim only serves legacy two-language bodies. Delete the shim before adding a third language, as its header says.
- The migration's `ELSE ARRAY['en']` and `CASE direction … ELSE ARRAY['en','vi']` are bounded by the guards, so they are correct.
- `conversationLanguagesOf` returns a pair, and `DirectionLabel` reads `languages[0..1]`. Both are two-language by design today.
- The literal grep (`'vi_to_en'`, `=== 'vi'`, `? 'vi' : 'en'`, `find(c => c !== x)`) finds nothing in apps/packages source outside the migration SQL and e2e fixtures.

## Pre-existing (not introduced, but amplified)

- A re-save after swapping direction post-conversation sends the NEW `settings.direction` (`use-conversation-save.ts:163,179`). It is now stored as `languages` flipped. Turn rows are still right because `sourceLanguages` comes from the segments. The history label flips, and `primaryTranslation` still picks the right text for two languages. Fix together with H1 by capturing the direction at conversation start.
- The plan's down-SQL (phase-06 step 9) puts its `array_length` guard AFTER `ADD COLUMN`/`UPDATE`. Move the guard first and wrap it in `BEGIN…COMMIT` before using it in the PR description.
